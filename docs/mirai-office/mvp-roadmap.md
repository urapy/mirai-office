# MVP開発ロードマップ

## リポジトリ構成

```text
mirai-office/
├── AGENTS.md              # みらいオフィスの開発規約
├── docs/
│   └── mirai-office/      # 企画、要件、調査、意思決定
├── core/                  # Pixel Agents由来コード
├── server/                # Pixel Agents由来コード
└── webview-ui/            # Pixel Agents由来の画面実装
```

企画文書とアプリコードを、みらいオフィス専用の単一Gitリポジトリで管理する。みらいオフィスのGitHubリポジトリを `origin`、Pixel Agents公式リポジトリを `upstream`、Pixel Agentsフォークを `pixel-agents-fork` とする。

## 進め方

### 0. フォーク基盤を用意する

- ローカル配置: 任意の作業ディレクトリにクローンしたリポジトリルート
- 上流リモート: `upstream`
- みらいオフィスのリモート: `origin`
- Pixel Agentsフォーク: `pixel-agents-fork`
- 開発ブランチ: `codex/mirai-office-mvp`

完了条件: `upstream/main` の更新を取り込め、みらいオフィスの変更を専用リポジトリと開発ブランチで管理できる。

状態: 完了

### 1. 画面移植スパイク

目的は、製品全体を作ることではなく「オフィス画面だけを子どもNISA用データで動かせるか」を確認すること。

1. 公式の開発手順で未変更版を起動する。
2. `webview-ui`、Canvas描画、経路探索、キャラクター状態の依存関係を調べる。
3. Claude/Codexイベントを使わず、固定JSONから3人を表示する。
4. 固定イベントから金額と会社・社会の説明を表示する。
5. 必要なコードと削除可能なコードを一覧化する。

完了条件: 仮想投資イベントだけで、3キャラクター、正確な口座数値、子ども向け説明を再現できる。ここで「フォークを継続」か「画面部分だけ移植」かを最終決定する。

状態: 進行中。未変更版のビルドと643テスト、`127.0.0.1:3100`でのHTTP配信を確認済み。描画・状態機械・経路探索の依存関係を整理し、Vite開発モードではClaude/Codexイベントを使わず固定JSONから3人を投入できる。固定価格、口座数値、架空ニュースまで接続済み。積立前後のチーム成長表現が残っている。

### 2. 仮想商品の価格シナリオを実装する

MVPは乱数だけにせず、説明しやすく再現可能な30日固定シナリオを先に作る。

確定した3シナリオ:

| シナリオ               | 目的             | 30日間のイメージ             |
| ---------------------- | ---------------- | ---------------------------- |
| でこぼこ成長           | 基本デモ         | 上下しながら最終的に約5%上昇 |
| 大きく下がって少し回復 | 下落時の学習     | 中盤で約10%下落し、少し回復  |
| ほぼ横ばい             | 利益保証を避ける | 横ばいと小幅下落で終了       |

各シナリオは同じ初期価格10,000、毎月の積立10,000円から始める。価格列と会社・社会の架空ニュースは固定JSONで管理する。損益とキャラクターの幸福度を結び付けず、値動きを一つの失敗だけで説明しない。

完了条件: 同じ入力で同じ結果になり、積立・評価額・損益の計算を単体テストできる。

状態: 進行中。3本×30日の固定JSON、架空ニュース、メモリ上の仮想口座を実装済み。10,000円の積立・自動購入、追加積立、日次評価、子ども・保護者画面切替を単体テストとビルドで確認した。積立頻度、平均取得価格、履歴表示、ローカル保存は未実装。

### 3. 画面設計

画面を先に増やさず、次の2画面と1つの切替導線に絞る。

- 子どもホーム: オフィス、元本、評価額、損益、会社・社会の短い説明
- 保護者ダッシュボード: 元本、評価額、損益、積立設定、履歴、シナリオ操作
- 保護者導線: 子どもが誤って管理操作へ入らないための明確な切替

低精細ワイヤーフレーム → クリック可能な静的画面 → 実データ接続の順で進める。各段階で8〜12歳向けの言葉と、保護者向け数値の正確さを確認する。

完了条件: 主要タスク、表示情報、空・下落・エラー状態が画面単位で定義されている。

### 4. 技術設計

画面移植スパイクの結果を受けて、次を決める。

- React/Vite/Canvasをどこまで継承するか
- 仮想口座のドメインモデルと投資イベント
- UI状態と金融計算の境界
- ローカル保存方式
- `127.0.0.1` のみで動かす起動方式
- テスト戦略とアクセシビリティ
- Pixel Agents由来ファイルと独自ファイルの境界

完了条件: コンポーネント図、イベントフロー、データモデル、テスト範囲、ライセンス台帳がそろう。

### 5. 縦切りMVPを実装する

最初の縦切りは「保護者が1回積み立てる → 子ども画面に仲間が増える → 日付を進める → 評価額・損益と説明が変わる」とする。その後、履歴、長期推移、学習カードを追加する。

状態: 進行中。保護者の積立、日付進行、評価額・損益、架空ニュース、子ども・保護者画面切替まで接続済み。積立ごとに仲間が1人ずつ増え、0〜3人でチームが成長する。次は投資履歴と長期推移の表示。

## 判断ゲート

次の段階へ自動的には進まない。

1. 画面移植スパイク後: フォーク継続か画面移植か
2. 価格シナリオ作成後: 教育表現と計算結果が妥当か
3. ワイヤーフレーム後: 子ども・保護者双方の操作が明確か
4. 技術設計後: セキュリティとライセンス境界を満たすか
